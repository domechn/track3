# Refresh source failures

`fetchPortfolios` runs one task per active exchange account, wallet address, and stock broker. ERC20 covers each configured EVM address; BTC, SOL, DOGE, TRC20, TON, and SUI cover each address on their respective chain. Manual `Others` entries form one local source. Addresses on the same chain run one at a time; BTC, DOGE, TON, ERC20, and TRC20 have a one second gap between addresses. Exchange, stock broker, SOL, and ERC20 tasks have a 120 second deadline to allow for sequential provider calls and rate limit retries. Other tasks have a 30 second deadline. A timed out task is excluded from the snapshot. In-flight provider calls can finish after the deadline; cache generations prevent their late results from repopulating cleared balance caches.

A primary balance exception, invalid holdings, or a deadline fails the source. A failure has a category of authentication/invalid key, network/timeout, rate limit, unsupported, or other. Upstream exception text and request URLs are never put in status messages, telemetry, or refresh toasts. A secondary product denied by permissions or explicitly not opened or enabled is treated as empty. Other secondary errors produce a **Partial** status with safe product names. Coinbase INTX portfolio 401 or 403 errors are an exception and produce a partial warning; a Coinbase default portfolio failure still fails the source. Unknown Solana tokens are skipped without failing the wallet. Listed tokens with a zero provider price are retained as in 0.8.2, preserving their holdings for the snapshot.

Each source status carries an alias, source kind, provider name, and a safe hint. Wallet addresses show their first six and last four characters. Exchange API keys show their first four and last four characters when long enough; short keys and broker accounts use a number within that provider. Colliding masked hints also fall back to provider numbers. Neither full keys nor broker tokens are kept in statuses. Saved status records are validated when read; older records without identification fields still show their original label. The dialog shows failed sources first, then stale, partial, and current. It counts failed and partial separately and provides a retry for each affected source. "Retry all failed" runs a full refresh to recheck the unavailable sources. A stale row shows when its holdings last succeeded if that time is known. Only fixed, safe error details and approved product names are shown.

**Snapshot policy:** a full refresh with at least one source holding fresh data saves those holdings and carries the last persisted amounts for failed wallet identities, including holdings worth less than $1. A **Partial** source saves its fetched balances exactly like an **OK** source; its older holdings are never substituted. Its warning names the unreadable products. If that source's fetched value at current prices is lower than its own stored value in the previous snapshot, the warning also says totals may be lower than usual. A price drop alone can trigger this wording. The comparison changes only warning text. When a source's identity is shared with another source, the comparison is omitted because the earlier contributions cannot be separated. Carried amounts use current prices when available and their saved baseline price if a fresh price lookup fails. Stale price lookups finish before the database write queue is acquired. A carried holding is shown as **Stale** in the source status dialog and creates no synthetic sale. When a failed identity has no saved holdings, it contributes no assets; the dialog shows **Failed** and warns that totals may be incomplete. A failed source is never written as a zero balance. If every source fails, no new history point is saved. The status button stays visible after closing the dialog, and its safe status metadata is stored locally so the warning remains visible after an app restart.

Manual entries can be attached to an exchange or chain wallet and therefore share its stored identity. If one of those sources fails, the saved row cannot be separated into its earlier contributions. Refresh retains that exact aggregate as stale until retry. This avoids double counting and an unproven sale.

**Single-source retry:** Retry clears fetch cache and loads only the selected account or address. It replaces that source's in-memory result from the completed refresh, combines the other source results, and commits a new history point against the latest persisted snapshot. A failed retry leaves the snapshot unchanged. Before committing, retry checks the configuration, the last committed refresh, and the persisted snapshot ID and contents. This also catches an import or deletion that did not create a refresh operation, including when no refresh was previously committed. If any check differs, retry asks for a full refresh so older source results cannot overwrite newer holdings. After an app restart, the warning remains visible; a full refresh is needed to restore the in-memory source results used by single-source retry.

Partial sources count as data present for portfolio alert evaluation. Insights identify partial sources separately from stale or failed sources and use only the alias and provider in their text. Sync copies the resulting snapshot amounts through its existing asset path; refresh statuses stay in local storage and accept older records without partial fields.

Currency rate updates are nonfatal. Price aggregation and database persistence remain shared steps: if either fails, the previous committed snapshot remains in place and refresh shows a generic error.
